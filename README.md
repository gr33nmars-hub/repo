# NOIR Casino Club

Учебное локальное казино на виртуальных демо-фишках. Приложение не принимает реальные деньги, не поддерживает платежи, депозиты или вывод средств.

## Запуск

Нужны Node.js, Rust (MSVC toolchain) и `uv`:

```powershell
uv sync
cd frontend
npm install
npm run tauri dev
```

Для разработки интерфейса в браузере запустите API и Vite в двух терминалах:

```powershell
# Корень проекта
uv run uvicorn --app-dir backend casino.api:app --host 127.0.0.1 --port 8765 --reload

# frontend/
npm run dev
```

API должен слушать loopback `127.0.0.1`. Для Windows-сборки из корня выполните `uv sync --group build`, затем в `frontend/` — `npm run tauri build`.

## Архитектура backend

```text
api.py       HTTP-модели, маршруты, преобразование ошибок; без игровых правил
session.py   CasinoSession: валидация намерения, orchestration, lock и атомарное сохранение
games.py     CasinoGame, правила конкретных игр, колода и инъецируемый SecureRandom
models.py    Player, Card, BlackjackHand и GameResult — доменные данные
storage.py   PlayerRepository: SQLite, импорт старого JSON, ledger и идемпотентность
```

`CasinoGame` задаёт небольшой полиморфный контракт игры; каждая реализация получает `RandomSource` и валидируемые правила через композицию. `CasinoSession` не содержит таблиц выплат: он связывает игру с профилем и хранилищем. `PlayerRepository` изолирует SQL от домена. Используются `threading.RLock` для последовательности действий внутри процесса и SQLite `BEGIN IMMEDIATE` для атомарного сохранения агрегата вместе с ledger и ключом запроса. Ограничение БД запрещает отрицательный баланс.

## Ставка и жизненный цикл

Для обычного раунда backend проверяет диапазон и баланс, вычисляет исход, затем одной SQLite-транзакцией сохраняет новый баланс, историю раунда, ledger-записи, готовый ответ и idempotency key. Ответ/ошибка не сообщают исход до успешной фиксации этой транзакции. Повтор того же ключа возвращает сохранённый ответ без повторного изменения баланса. Клиент сохраняет ключ до получения успешного ответа, поэтому сетевой повтор остаётся идемпотентным.

Блэкджек списывает начальную ставку при старте и сохраняет карты, оставшуюся колоду, флаг натурального блэкджека и состояние хода. После перезапуска активная раздача восстанавливается. Каждое разрешённое действие обновляет сохранённое состояние транзакционно; `double` списывает дополнительную ставку, а завершение записывает выплату и результат. При целочисленных фишках ставки блэкджека должны быть чётными, чтобы выплата 3:2 оставалась точной.

## Правила и выплаты

Лимиты ставок находятся в `GameRules`, blackjack — в `BlackjackRules`, рулетка — в `RouletteRules`, слоты — в `SlotRules`. Конфигурации проверяются при создании. Изменяйте параметры там, а не в HTTP-обработчиках.

- **Европейская рулетка:** равномерный выбор кармана `0..36`; красные номера заданы в `RED_NUMBERS`, остальные ненулевые — чёрные. Красное/чёрное возвращают `2 × ставка` (ставка включена); зеро возвращает `36 × ставка` (35:1 выигрыш плюс ставка). Существующие варианты UI/API — `red`, `black`, `zero`.
- **Блэкджек:** туз считается за 11 и понижается до 1 при переборе; дилер стоит на soft 17 по умолчанию. Натуральный блэкджек платит `ставка × 5 / 2` вместе со ставкой, обычная победа — `2 × ставка`, push — `ставка`, проигрыш — 0. Натуральный блэкджек — только исходная пара из двух карт; 21 после добора платится как обычная победа.
- **Слоты:** каждый из трёх барабанов имеет явно заданную последовательность символов, повтор символа задаёт его вес. Тройка платит настроенный множитель от 2× до 15× (включая ставку), пара возвращает 1×, прочее — 0. UI не заявляет RTP/вероятности.

Все игры используют `secrets` через `SecureRandom`. Система **не заявляет Provably Fair**: seed/nonce commitment и независимой проверки исхода нет.

## Хранилище и перенос профиля

SQLite-файл по умолчанию: `~/.noir-casino/casino.sqlite3`. При первом создании базы профиль `~/.noir-casino/player.json`, включая активное состояние блэкджека, импортируется в транзакции. Исходный JSON не удаляется. Если файл повреждён или активная раздача не проходит проверку, запуск завершается с ошибкой вместо тихого сброса прогресса. Можно задать `NOIR_CASINO_SAVE_PATH` на путь SQLite; для совместимости заданный путь с суффиксом `.json` означает соседний `.sqlite3` и этот JSON источник миграции.

Таблица `ledger` содержит движения виртуальных фишек и баланс после записи; `processed_requests` хранит использованные ключи. Ключи создаёт frontend (`crypto.randomUUID()`) и отправляет с каждым изменяющим запросом. SQLite обеспечивает транзакционную атомарность данных в локальном single-player приложении; сервер рассчитан на один локальный backend-процесс.

## HTTP API

Маршруты и формы ответов state/history сохранены. Для POST, меняющих состояние, обязателен `idempotency_key`:

```http
GET  /api/health
GET  /api/state
POST /api/games/roulette/play
Content-Type: application/json
{"bet": 20, "choice": "zero", "idempotency_key": "uuid"}

POST /api/blackjack/start
{"bet": 20, "idempotency_key": "uuid"}

POST /api/blackjack/action
{"action": "stand", "idempotency_key": "uuid"}

POST /api/refill
{"idempotency_key": "uuid"}
```

Ошибки доменной валидации идут как HTTP 400 с `detail`; request validation FastAPI возвращает HTTP 422 с тем же полем `detail`. Повторный запрос с тем же ключом вернёт ранее сохранённый ответ. API предназначен только для loopback-доступа.

## ООП на защите

- **Инкапсуляция:** `Blackjack` владеет состоянием колоды/руки и проверяет действия только в активном состоянии.
- **Абстракция:** `CasinoGame.play()` и `RandomSource` задают минимальные контракты.
- **Полиморфизм:** `CasinoSession` публикует сведения об играх и запускает конкретную игру через общий контракт.
- **Композиция:** игра получает RNG и конфигурацию правил; session получает репозиторий; HTTP слой зависит от application service.
- **Разделение ответственности:** транспорт, orchestration, правила домена и SQL находятся в отдельных модулях.
