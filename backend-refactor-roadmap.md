## 2. Карта зависимостей и жизненного цикла

```text
frontend/src/{lib/casino.api.ts,hooks/useCasino.ts,types.ts,features/*}
  -> HTTP /api/* -> backend/casino/api.py (Pydantic, middleware, HTTP-ошибки)
  -> singleton CasinoSession в api.py
       -> core.py: CasinoGame, GameRules, RandomSource
       -> games.py: SlotMachine, Roulette
       -> blackjack.py: Blackjack, BlackjackRound, PlayerHand, BlackjackRules
       -> models.py: Player, GameResult, Card
       -> storage.py: PlayerRepository -> SQLite profile/ledger/processed_requests/metadata
```

`POST play`: Pydantic -> lock сессии -> поиск ключа в БД -> проверка игры/ставки/баланса -> случайный исход -> изменение `Player` в памяти -> `GameResult` и state -> `save`: `BEGIN IMMEDIATE`, запись профиля/ключа/ledger, commit -> ответ. Исключение до commit откатывает БД и снимок `Player` в этой сессии.

`POST blackjack/start`: ключ -> проверка незавершённой раздачи и ставки -> списание -> при необходимости новый шестиколодный башмак -> четыре карты -> insurance при тузе дилера, иначе peek; если раздача завершена, выплата и история -> единый `save` профиля, снимка рук/башмака/сброса, ledger и ответа. `POST blackjack/action`: проверка `available_actions` -> `hit/stand/double/split/surrender/insurance` -> возможное дополнительное списание -> переход к следующей руке или ход дилера -> выплата/история -> `save`. Снимок восстановлен при создании `CasinoSession`; `GET state` читает **память**, а не новую версию БД.

Схема сохранения: одна строка `profile` содержит баланс, всю историю JSON и раздачу JSON; `ledger` — движения; `processed_requests` — ключ, подпись и полный ответ; `metadata` — отметка импорта. Ветвь старого `player.json` импортирует профиль и раздачу при первой инициализации. `BEGIN IMMEDIATE` охватывает только `save`; загрузка и расчёт идут до него. `RLock` защищает только один объект в одном процессе.

## 3. Источники, обязательные правила и варианты

Первичные источники: [Python 3.10 `sqlite3` и explicit transaction control](https://docs.python.org/3.10/library/sqlite3.html), [Python `secrets`](https://docs.python.org/3.10/library/secrets.html), [SQLite transactions, `BEGIN IMMEDIATE`](https://www.sqlite.org/lang_transaction.html), [SQLite isolation/WAL](https://www.sqlite.org/isolation.html), [FastAPI request validation/exception handlers](https://fastapi.tiangolo.com/tutorial/handling-errors/), [FastAPI response models](https://fastapi.tiangolo.com/tutorial/response-model/), [Nevada Gaming Control Board: GameAce Live Blackjack rules](https://www.gaming.nv.gov/siteassets/content/divisions/technology/rules-of-play/gameace-live-blackjack.pdf), [Nevada Gaming Control Board: Roulette rules](https://www.gaming.nv.gov/siteassets/content/divisions/enforcement/rules-of-play/Roulette.pdf), [UK Gambling Commission: theoretical vs actual RTP](https://www.gamblingcommission.gov.uk/authorities/codes-of-practice/guide/page/how-to-calculate-return-to-player-rtp). Эти материалы применяются как описание механики и математики, **не как регуляторные требования** к виртуальным фишкам.

Текущий продукт выбирает: европейское колесо 0–36; ставки только `red/black/zero`, возврат со ставкой 2×/36×; шесть колод; дилер стоит на soft 17; peek; натуральный blackjack 3:2; insurance половина ставки с выигрышем 2:1; поздняя сдача, double на первых двух картах и после split; максимум четыре руки, split 10/J/Q/K по номиналу, split aces получают одну карту и не делятся повторно. В источнике по blackjack некоторые параметры **конфигурируемы** (H17/S17, 3:2/6:5, условия double/split/surrender), а его Seven Card Charlie — особенность конкретного варианта, не правило этого проекта. Общий документ по рулетке допускает 0 **или** 00, проект выбирает одно 0. Не менять набор правил без продуктового решения и фиксации версии правил в сохранениях.

Для текущих слотов три независимых выбора из восьми позиций каждого барабана дают 512 равновероятных комбинаций. Вес тройных выплат: `27·4 + 8·4 + 1·8 + 1·12 + 1·24 = 184`; ровно 270 пар платят 1×, прочие 204 — 0. Теоретический RTP `(184+270)/512 = 88.671875%`, UI показывает округлённые 88.7%. Это математическое ожидание по **возврату со ставкой**, не наблюдаемый RTP короткой сессии. Для европейской рулетки ожидаемый возврат цвета и зеро одинаков: `36/37 ≈ 97.2973%`; house edge `1/37`. Эти числа следуют из текущих весов/выплат и правил, а не предписывают целевой RTP.

## 5. Целевая архитектура и решения

```text
api.py / api_schemas.py: только транспорт, строгие DTO, стабильные коды ошибок
session.py: application service, use cases, запрос по ключу, orchestration транзакции
storage.py: SQLite unit of work / repository, schema migrations, reconciliation
models.py: PlayerSnapshot, ChipMovement, RoundResult, Card — проверяемые value objects
core.py: GameRules, typed RNG, компактный контракт one-shot игры
games.py: чистые slot/roulette outcome + payout, конфигурация и odds
blackjack.py: BlackjackRound aggregate, transitions, rule version, settlement effects
```

Направление зависимостей: transport -> application -> domain interfaces/values; storage реализует требуемый application протокол. `blackjack.py` и `games.py` не импортируют API/SQLite, `storage.py` импортирует только сериализуемые доменные снимки/codec (убрать поздний импорт `Blackjack` из `storage.py:92-93` посредством явного decoder/migrator). Внешний `CasinoSession` можно сохранить как совместимый фасад на время перехода.

ООП для защиты проекта: **инкапсуляция** — `BlackjackRound` владеет фазой, руками и башмаком, изменение только методами перехода с предусловиями; **абстракция** — один `RandomSource` и узкий repository/UoW protocol нужны для детерминированных тестов и замены IO; **полиморфизм** — каталог one-shot игр вызывает общий `play` у `SlotMachine`/`Roulette`, blackjack сознательно имеет отдельный протокол; **наследование** — `CasinoGame` используется только там, где один и тот же контракт действительно выполняется (возможна замена ABC на Protocol, если она упростит код); **композиция** — blackjack получает rules/RNG, session получает repository. SRP — по границе transport/application/domain/persistence; DIP — только на границе IO; OCP не означает обещания неограниченно подключаемых игр; LSP не требует заставлять blackjack наследовать `CasinoGame`; ISP — малые контракты. Проверяемое проявление каждого принципа важнее количества классов.

Решения и альтернативы:

| Вопрос | Выбор и причина | Альтернатива/условие пересмотра |
|---|---|---|
| Конкуренция | Одна операция = `BEGIN IMMEDIATE`, загрузка свежего aggregate и ключа внутри транзакции, в конце проверка version/CAS и ledger equation. SQLite локален и уже используется. | Только `RLock` не охватывает другой объект/процесс. Отдельный actor-процесс уместен лишь если desktop lifecycle станет жёсткой гарантией single writer. |
| Ledger | Profile balance как материализованное состояние, ledger как проверяемый журнал с opening entry. | Вычислять баланс только суммой ledger: дороже и требует честного переноса legacy; можно перейти после полной миграции и backfill. |
| Модель blackjack | Отдельный stateful aggregate; one-shot игры через существующий узкий контракт. | Общий `Game` с start/action/settle породит пустые методы и ослабит типы. |
| Выплаты | `int` фишки, payout включает возвращаемую ставку, натуральное 3:2 только при допустимом номинале. | Дробные фишки/Decimal нужны лишь при продуктовой смене номинала или paytable. |
| Состояние сохранения | Schema/rule version + строгие миграторы; известный deck сохранить, неизвестные исторические карты не изобретать. | Молчаливый reset раздачи/баланса неприемлем. |
| HTTP | Стабильные текущие URL/поля, сначала добавить явные DTO и коды ошибок; breaking change только через versioned endpoint/адаптер. | Одномоментный breaking rename вынудит frontend и сохранённые ответы менять синхронно. |

## 7. Матрица критических инвариантов

| Инвариант | Проверка |
|---|---|
| `balance >= 0`; `new = old + Σ movements`; каждый `balance_after` совпадает с префиксной суммой; нет изменения без ledger | SQLite integration + property/model-based последовательности play/start/action/refill, corruption fixture, независимый SQL reconciliation |
| Одно действие с одним ключом и payload производит не более одного settlement; тот же ключ с иным payload даёт conflict | HTTP lost-response/retry, конкурентные процессы, рестарт frontend/backend, legacy ambiguous key |
| Profile, hand, shoe, history, ledger и cached response фиксируются или откатываются вместе | Fault injection на draw, JSON encode, каждую SQL запись, commit/busy; сравнение БД и memory после reload |
| Ставки и выплаты blackjack — целые: natural 5b/2, win 2b, push b, surrender b/2; split/double/insurance списаны ровно раз | Deterministic transition table, recovery after each action, split/resplit/aces, dealer natural/no natural, S17/H17 конфигурация |
| Суммарный состав шести колод 312 карт и каждая rank/suit встречается 6 раз среди deck+discard+active; известный deck order сохраняется | Save/restore round trips и corrupted inventory fixtures; near-cut-card tests |
| Roulette uniform 37 pockets, red/black по 18, zero 1; payout 2b/36b | Exhaustive 37-outcome oracle по каждому выбору, property bet range |
| Slots ровно 512 равновероятных stop triples, 38 triples/270 pairs/204 losses; RTP 454/512 | Exhaustive enumeration независимо от production `theoretical_return_percent`; metamorphic test изменённых reel weights/paytable |
| История, статистика, wire response и frontend state описывают один committed результат | API snapshot/OpenAPI+TS fixtures; integration проверка `rounds_played`, wins/losses, history order и restart |

Тестовая иерархия: быстрые детерминированные unit tests правил на fixed RNG/deck; исчерпывающие конечные пространства roulette/slots; property/model-based последовательности баланс/blackjack; integration tests реального SQLite и двух процессов; ASGI HTTP/contract tests; smoke desktop sidecar. Статистический тест RNG не заменяет математический oracle и не должен падать случайно в CI.

## 8. Определение «готово» для backend ранней альфы

- Все заявленные правила v1 и формулы опубликованы в API/UI, подтверждены независимыми oracle tests; нерешённые варианты помечены как продуктовые вопросы.
- Нет известного сценария двойной выплаты, потерянного действия, отрицательного/необъяснимого баланса или молчаливой порчи сохранения. Один SQLite-файл поддерживает безопасный рестарт и повтор запроса; multi-process доступ либо корректен, либо явно запрещён и проверяется до открытия.
- Старые поддерживаемые сохранения переносятся идемпотентно с backup; повреждённые не перезаписываются. Profile, ledger, history, hand и cached response согласованы после каждого commit.
- Текущие frontend контракты и статусы сохранены или версионированы; ошибки различают invalid action, insufficient chips, key conflict, corrupted save и временную занятость БД. Packaged sidecar проверен на loopback/token.
- Тесты проходят на минимальном Python 3.10 и выбранном актуальном Python, frontend build/lint зелёные; инструкция запуска тестов воспроизводима из корня. Оставшийся P2 долг имеет владельца и не маскирует correctness.

## 9. Принятые решения для ранней альфы

- `refill` доступен только после завершения blackjack-раздачи. Это сохраняет доступные `double`/`split` неизменными в середине руки.
- Существующие правила рулетки, блэкджека и слотов считаются правилами v1; эта реализация не меняет soft 17, страховку, surrender, ограничения split/double, paytable или strip weights.
- Демо-фишки остаются локальным игровым счётом без платежей, депозитов, вывода и требований оператора реального казино. Slot commit/reveal реализован как пользовательская проверка локального результата, а не обязательная compliance-система.

## 10. Статус реализации

### Готово в текущем рабочем дереве

- Полное `BEGIN IMMEDIATE` охватывает refresh агрегата, поиск idempotency key, проверку, игровой переход, ledger/profile запись и cached response. `profile_revision` обновляется в той же транзакции; API state перечитывает revision перед ответом. Тесты покрывают конкурирующие разные операции и повтор одного ключа из двух сессий.
- Ledger получает opening balance при первом запуске/миграции; startup проверяет цепочку и равенство итога профилю. Каждая запись проверяет совпадение суммы ledger movements с изменением баланса, а затем целиком проверяет цепь до commit. Несоответствие откатывается или останавливает загрузку.
- Профиль и история больше не преобразуют строки/отрицательные значения в значения по умолчанию; `Player` и `GameResult` проверяют входы. Карта стала immutable value object. `Player.debit/credit` централизуют арифметику фишек.
- Legacy idempotency rows без signature теперь возвращают HTTP 409 и не привязываются к первому случайному повтору. API получил строгие input schemas и response schemas без изменения URL/публичных полей; unknown roulette choice по-прежнему даёт HTTP 400.
- Клиент сохраняет pending key вместе с endpoint/payload в localStorage, блокирует новое действие при неизвестном исходе и повторяет прежнее тело после перезапуска. При 409 сначала перечитывает серверное состояние; если это удалось, удаляет только подтверждённый конфликтующий ключ и даёт актуальный state UI.
- Пополнение запрещено во время активной blackjack-раздачи. RNG интерфейс типизирован; таблица игр строится через `catalog_info()` без `isinstance(SlotMachine)`.
- Добавлены исчерпывающие oracle tests на 512 исходов слотов и 37 pocket каждого варианта рулетки; тесты гонок, ledger migration/corruption, strict API DTO и HTTP 409. Установлены project quality commands (Ruff/mypy).
- SQLite schema version проверяется через `PRAGMA user_version`; неизвестную более новую схему старый backend не открывает. `player.json` копируется до импорта. Модуль `casino.recovery` создаёт согласованные SQLite backups, проверяет копии вместе с profile/ledger/рукой и восстанавливает их через staging-файл; перед заменой назначения оставляет его копию.
- Новые blackjack rounds имеют устойчивый id; ставки, double, split, insurance и payout записываются с этим id. Активный snapshot сверяется с суммой ставок ledger и начальной ставкой. Снимки старых версий без id продолжают читаться и маркируются как legacy, для них cross-check ставок пропускается.
- `Blackjack.act()` возвращает immutable ledger effects вместе с результатом; application service применяет только валидированные movements к `Player`. Проверены rollback руки/башмака при отказе save и действие restore на старом активном snapshot.
- Детеминированный model-based trace выявил, что `Blackjack.act("insurance")` проверял доступность по фазе `insurance`, а затем ошибочно требовал `playing`; dispatch теперь требует фактическую фазу. Trace повторно создаёт session после каждого действия и сверяет non-negative balance, результат и aggregate ledger.
- В текущем рабочем дереве добавлен commit/reveal слотов. Сервер принимает client seed и ожидаемый hash, использует HMAC-SHA-256 с rejection sampling, сохраняет новый commitment атомарно с результатом и ledger, а браузер перепроверяет seed/позиции/выплату. Stale hash даёт HTTP 409 и UI сверяет state. Это проверка локальной игры, не заимствованное регуляторное требование.
- `run_api.py` сохраняет loopback bind и стандартный порт 8765, но позволяет указать отдельный локальный порт для smoke/разработки. Собранный PyInstaller sidecar прошёл HTTP smoke: nonce, токен, состояние, commit/reveal, повтор ключа и stale commitment.
- Frontend `node:test` проверяет точную сериализацию pending endpoint/payload при перезапуске store, in-memory fallback при запрете localStorage, malformed storage и совпадение браузерного HMAC verifier с backend вектором, включая отказ при изменённых stop/symbol/payout/commitment.
