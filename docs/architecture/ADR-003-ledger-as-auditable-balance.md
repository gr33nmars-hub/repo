# ADR-003: Ledger хранит движения фишек

## Статус

Accepted

## Контекст

Профиль хранит текущий баланс для быстрых запросов. Одного значения баланса недостаточно, чтобы проверить причину изменения. SQLite уже хранит ledger и обработанные idempotency keys.

## Рассмотренные варианты

| Вариант | Выгода | Цена |
|---|---|---|
| Материализованный баланс и ledger | Быстрый профиль и проверяемая последовательность движений. | Требуется проверять равенство баланса сумме журнала и безопасно переносить старые базы. |
| Баланс только из суммирования ledger | Один источник истины для суммы. | Каждое чтение профиля требует прохода по журналу; миграция legacy данных остается сложной. |

## Решение

Сохранять баланс профиля и append-only movements в одной транзакции. Каждый изменяющий запрос сохраняет signature, ответ и ledger entries с одним idempotency key; новые завершённые игровые rounds получают immutable `round_id`, связывающий историю с ledger entries. При загрузке проверяются цепочка `balance_after`, итоговый баланс и эта связь для новых one-shot rounds.

## Последствия

- Неизвестная provenance старого журнала требует явной диагностики, а не автоматического исправления.
- Профиль нельзя записать с изменившимся балансом без явного movement.
- История игровых результатов не заменяет ledger: это разные данные и разные инварианты.

## Пересмотреть, если

Появится измеренная проблема производительности или миграция докажет, что старые данные нельзя представить этим журналом без потери смысла.
