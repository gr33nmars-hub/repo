# ADR-005: Разделить desktop lifecycle и API transport

## Статус

Accepted

## Контекст

React интерфейс вызывает локальный API. В production Tauri создает sidecar с token и nonce; в dev backend запускается отдельно. HTTP запросы и управление процессом находились в одном модуле, а клиентские DTO поддерживаются вручную.

## Рассмотренные варианты

| Вариант | Выгода | Цена |
|---|---|---|
| Platform lifecycle, HTTP transport и game commands в отдельных модулях | Shell API и политика retry не смешиваются с HTTP сериализацией. | Несколько небольших модулей и контрактные проверки TS/OpenAPI. |
| Один API модуль | Меньше файлов. | Транспортные изменения затрагивают sidecar lifecycle; контракт Python/TS расходится незаметно. |
| Генерировать TypeScript DTO из OpenAPI сейчас | Один контракт. | Добавляет генерацию и обновление артефактов к каждому изменению API. |

## Решение

`platform/desktopBackend.ts` запускает, проверяет и завершает sidecar; `lib/httpClient.ts` выполняет HTTP запросы; `lib/casino.api.ts` хранит игровой API и pending mutation retry; `lib/apiConfig.ts` задает адрес. Пока оставить типы TypeScript вручную, добавляя контрактные проверки против FastAPI схем.

## Последствия

- Публичные API URL и payload сохраняются во время внутреннего переноса.
- Изменение адреса требует согласованной проверки client и Tauri CSP.
- Vite build не заменяет smoke установленного приложения.
- Если ручные DTO начнут регулярно расходиться, сгенерировать типы из OpenAPI.

## Пересмотреть, если

Появится другой desktop host, второй API клиент или частые API изменения, при которых ручная синхронизация становится источником ошибок.
